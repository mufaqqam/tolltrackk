# Vibe coding log: real issues found in AI-generated code

TollTrack was built with AI-assisted coding (Claude). This log records problems found in the AI's output during the build: what went wrong, how it was caught, and what fixed it. These are the concrete examples for the risk analysis in the Assessment 3 video.

| # | Area | What the AI-generated code did | How it was caught | Fix (conventional method) | Risk category |
|---|------|--------------------------------|-------------------|---------------------------|---------------|
| 1 | Suggestion engine | First version mixed "km along the toll road" with "straight-line km" in one formula. Long, curving trips (e.g. Fawkner → Kooyong on CityLink) looked like detours and the correct exit (Monash Fwy / Toorak Rd) was rejected. | Ran a table of 12 real Melbourne trips and checked each answer by hand. | Used one unit (straight-line km) for every comparison; kept road km only for display. Added the trips as unit tests so it can't silently break again. | Reliability / hard to verify |
| 2 | Suggestion engine | First confidence formula marked about two-thirds of normal trips as "needs check". The code ran fine, but it would have annoyed drivers and defeated the purpose. | Same manual test table; compared scores with what a driver would expect. | Recalibrated the formula and fixed the threshold at 70% as a named constant (`CHECK_THRESHOLD`), not a magic number. | Quality / usability |
| 3 | Reference data | The AI can produce plausible coordinates for toll ramps from memory, but they are only approximate (about 300–800 m out). Names were checked against Linkt's published price guide; coordinates were not surveyed. | Cross-checked names against the Linkt CityLink pricing PDF (Jul–Sep 2026) and EastLink's interchange list. | Labelled the data as approximate in the file itself; the driver always confirms or edits the suggestion; a production version would load official GIS data. | Data accuracy / verification |
| 4 | Dates and time zones | The generated office pages converted timestamps to dates with `toISOString()`, which uses UTC. Melbourne is UTC+10/11, so anything done before 10–11 am Melbourne time (e.g. a 7 am sign-in or upload) showed the previous day's date. | Code review of every date conversion (search for `toISOString`). | Added one helper (`melbourneToday`) that always uses the Australia/Melbourne zone and used it everywhere. | Reliability / subtle bug |
| 5 | Database seed script | AI-written SQL `date + time at time zone 'Australia/Melbourne'` failed: `AT TIME ZONE` binds tighter than `+`, so it applied to the wrong part. | The seed script crashed on first run against a real PostgreSQL database. | Added brackets; the seed now runs as part of setup. Testing against a real database, not just reading the code, caught it. | Reliability |
| 6 | Statement matching (billing) | The generated matching code had a second "near miss" pass that paired any leftover charge with any leftover trip on the same day, truck and toll road. An unrelated EastLink toll (Princes Hwy → Thompson Rd) was attached to job A-4479 (High Street Rd → Burwood Hwy). This hid a toll nobody logged (money the business loses) and pointed the office at the wrong job; if the office accepted it, that customer would be billed for a toll they didn't cause. | Reviewing the demo results screen: the "Check" row made no sense to a person who knows the roads. The code ran without errors and every automated check still passed. | A near miss must now share the entry or the exit point. Added a regression unit test with this exact case. | Security/ethics of billing data · hard to verify |
